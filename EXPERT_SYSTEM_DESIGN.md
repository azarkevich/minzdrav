# Экспертная система «Разрешено ли исследование при диагнозе» — дизайн

Вопрос пользователя: *«Диагноз — аутоиммунный тиреоидит, разрешён ли анализ мочи по Ничипоренко?»*
Ответ: предусмотрено ли исследование клиническим протоколом МЗ РБ для этого диагноза,
в каком статусе, с **дословной выдержкой из протокола и ссылкой `URL#page=N`**.

**Принятые решения (22.10.2026):**
- Пользователь — сотрудник страховой компании, который решает, является ли случай страховым.
  «Разрешено» значит «предусмотрено протоколом для этого диагноза». Нужна выдержка из файла
  и ссылка на него (URL и страница).
- Справочник услуг — перечень из постановления МЗ №123.
- **Врач базу не проверяет.** Поэтому достоверность обеспечивается автоматическими перекрёстными
  проверками (§2.2а), а не ручной проверкой. Каждый ответ обязан содержать цитату, чтобы
  страховщик мог проверить его сам за несколько секунд.

**Статус:** этапы 0, 1 и прототип этапа 2 сделаны, см. §5. База знаний — JSON (`kb/kb.json`), не SQLite: для прототипа проще.

## 1. Что показали сами протоколы

Разбор «КП … заболеваниями щитовидной железы (взрослые), пост. №85 от 21.06.2021» и выборки остальных:

1. **Ответ не бинарный.** Протоколы делят диагностику на
   - *обязательную* — «минимальный комплекс медицинских услуг … на любом уровне»;
   - *дополнительную* — «необходимость … определяется по результатам обязательной диагностики»,
     часто с условием («ТАБ … при TI-RADS 3 и более»);
   - исследования в *плане наблюдения* (контроль ТТГ ежегодно, УЗИ 1 раз в 2 года) и перед лечением.

   Кроме того, в общих положениях (п. 4) сказано: *«могут применяться иные, не указанные в данном
   клиническом протоколе медицинские услуги … назначенные по результатам консультации
   врача-специалиста в соответствии с протоколом … сопутствующего заболевания»*. Поэтому «не указано»
   не значит «запрещено» — так ответ и нужно формулировать.
2. **Диагностика наследуется.** Глава 12 «Хронический аутоиммунный тиреоидит» содержит только
   критерии и лечение, а списки обязательной и дополнительной диагностики находятся в общей главе 6
   «Тиреоидиты» (пп. 73–74, коды E06.0–E06.5, O90.5). Поиск фрагментов по сходству с вопросом (RAG)
   найдёт главу 12 и ошибётся.
3. **Отрицательный ответ требует полноты.** Чтобы сказать «Ничипоренко не предусмотрен», нужно знать
   *весь* список исследований для диагноза. Ни поиск по сходству, ни LLM «по памяти» этого не гарантируют.
   Нужна структурированная база.
4. **Формулировки разнородные:** сокращения и группы («ОАК; БАК: АЛТ, АСТ, С-реактивный белок»,
   «исследование гормонов крови: ТТГ, АТ-ТПО»), расплывчатые пункты («лабораторные тесты,
   подтверждающие тиреоидит»), в старых протоколах — таблицы и пометка `*` у дополнительных методов.
5. **Покрытие** (по итогам этапа 1, `parsed/coverage.csv`): из 400 PDF
   - 319 типовых (главы и пронумерованные пункты);
   - 55 табличных (старые протоколы 2005–2012 и крупные сводные: урология, ЛОР, эндокринология
     для детей, акушерство). Таблица вида «нозология (МКБ) | обязательная | кратность |
     дополнительная | лечение» удобна для нашей задачи, но после извлечения текста колонки
     перемешиваются. Их нужно разбирать по позициям колонок (строка-шапка «1 2 3 4 5») или по
     изображению страницы;
   - 17 без глав;
   - 9 сканов: текстом распознана только обложка приказа, нужен OCR.

   В 370 документах найдены коды МКБ-10. Одному диагнозу могут соответствовать несколько
   протоколов: для взрослых и детей, разных специальностей.
6. **Формулировки списков диагностики не единообразны:** «Обязательная диагностика:»,
   «Для постановки или подтверждения диагноза осуществляются: …; дополнительные инструментальные
   и лабораторные исследования: …» (стоматология), исследования внутри «обязательных лечебных
   мероприятий». Регулярные выражения находят маркер «обязательная диагностика» только в 260
   документах из 400.
7. **Перечень №123** содержит не только отдельные анализы, но и комплексы класса B03:
   «Анализ мочи общий» B03.014.006, «Общий (клинический) анализ крови» B03.014.002,
   «Анализ крови биохимический общетерапевтический» B03.014.004. Проба Нечипоренко —
   отдельная услуга A09.28.060 «Подсчет количества форменных элементов методом Нечипоренко»,
   в ОАМ она не входит.

**Вывод:** нужна база знаний «диагноз → исследование → статус», извлечённая заранее (офлайн) с
проверкой человеком. LLM нужен на двух краях: извлекать данные из PDF при построении базы и разбирать
вопрос пользователя. Решение «разрешено / не разрешено» принимает детерминированная логика по базе.

## 2. Архитектура

```
                    ОФЛАЙН (при изменении protocols/)                     ОНЛАЙН (запрос)
┌──────────┐  ┌─────────────┐  ┌──────────────┐  ┌──────────────┐     ┌─────────────────────┐
│ scraper  │→ │ 1. parser   │→ │ 2. extractor │→ │ 3. normalizer│     │ UI: CLI / web / MCP │
│protocols/│  │ структура   │  │ LLM → JSON   │  │ каталог услуг│     └─────────┬───────────┘
└──────────┘  │ гл./пункты/ │  │ + проверка   │  │ МКБ-10       │               ▼
              │ МКБ, стр.   │  │ цитат        │  │ синонимы     │     ┌─────────────────────┐
              └─────────────┘  └──────────────┘  └──────┬───────┘     │ query parser (LLM): │
                                                       ▼              │ диагноз, услуга,    │
                                              ┌─────────────────┐     │ возраст             │
                                              │ kb.sqlite       │◄────┤ resolver → engine   │
                                              │ + 4. review UI  │     │ → ответ + цитаты    │
                                              │ (врач)          │     └─────────────────────┘
                                              └─────────────────┘
```

Ядро — Python-пакет `minzdrav_kb`. Интерфейсы — тонкие обёртки над ним.

### 2.1 Parser (развитие `protocol_chapter_extractor.py`)

Разбирает документ целиком, а не одну главу, в дерево:
`документ → глава → пункт (73.) → подпункт (73.1) → строки`; у каждого узла есть страница, текст,
найденные коды МКБ и раскрытые сокращения (glossary уже есть). Результат:
`kb_build/<doc_id>/structure.json`, где `doc_id` — sha256 из `manifest.json`. Так при обновлении
протокола заново обрабатывается только он.

Метаданные документа берутся из `index.csv` и титульного листа: название, номер и дата
постановления, население (взрослые/дети), специальность.

### 2.2 Extractor (LLM, офлайн)

На каждый документ — один или несколько вызовов LLM (Claude уровня Opus) со структурой документа на
входе и строгой JSON-схемой на выходе:

```json
{
  "sections": [{
    "section_id": "гл6",                // где лежат списки диагностики
    "applies_to": {                     // к каким диагнозам относится
      "icd10": ["E06.0","E06.1","E06.2","E06.3","E06.4","E06.5","O90.5"],
      "names": ["тиреоидит", "аутоиммунный тиреоидит", "тиреоидит Хашимото", "..."],
      "population": "adult"
    },
    "inherited_by": ["гл7","гл8","гл9","гл10","гл11","гл12","гл14","гл15"],
    "items": [{
      "raw": "исследование гормонов крови: ТТГ, АТ-ТПО",
      "split": ["ТТГ", "АТ-ТПО"],
      "level": "mandatory",             // mandatory | additional | monitoring | pre_treatment
      "condition": null,                // «при TI-RADS 3 и более» и т.п.
      "clause": "73", "page": 50,
      "quote": "исследование гормонов крови: ТТГ, АТ-ТПО"
    }]
  }]
}
```

Защита от галлюцинаций, без неё в медицине нельзя:
- каждая `quote` обязана **дословно** (после нормализации пробелов и переносов) найтись в тексте
  указанного пункта, иначе запись отклоняется;
- контроль полноты: все строки внутри блоков «Обязательная / Дополнительная диагностика», найденные
  регулярками, должны попасть в `items`; расхождения идут в отчёт;
- результат кэшируется по `(doc sha256, версия промпта)`.

Типовые протоколы (около 360) по большей части можно разобрать правилами, без LLM: блоки «NN.
Обязательная диагностика:» / «Дополнительная диагностика:» имеют устойчивую форму. LLM нужен для
связи «раздел → диагнозы», для наследования, условий и нетиповых форматов. Разумно сделать оба
способа и сверять: расхождение — сигнал проверить вручную.

### 2.2а Проверки вместо врача

Врача нет, поэтому запись попадает в базу как `verified` (автоматически) только при выполнении всех
условий:
1. цитата дословно найдена в тексте пункта (§2.2);
2. два независимых способа извлечения дали одно и то же: правила и LLM либо две разные LLM.
   Сравниваются набор услуг, статус (обязательная/дополнительная) и раздел;
3. сопоставление с перечнем №123 однозначное: точное совпадение, синоним из словаря или выбор LLM
   с высокой уверенностью, подтверждённый вторым прогоном.

Остальные записи получают статус `uncertain`. Они участвуют в ответе, но с пометкой «требует
проверки по цитате». Поскольку страховщик и так видит цитату и ссылку, такая пометка безопасна.
Расхождения собираются в отчёт, по которому можно дорабатывать правила и промпты.

### 2.3 Normalizer — справочник услуг и диагнозов

Это самая трудоёмкая часть.

- **Каталог медицинских услуг** — перечень из постановления МЗ №123 (`reference/services.json`):
  7055 услуг, 3191 из них диагностические. Протоколы прямо ссылаются на этот перечень. У каждой
  услуги есть код, название, тип (A09 — исследования биологических жидкостей, A06 — рентген, B03 —
  диагностические комплексы…) и область. Поверх перечня нужны:
  - словарь синонимов и сокращений: «ОАМ» → B03.014.006; «проба / анализ мочи по
    Нечипоренко (Ничипоренко)» → A09.28.060; опечатки;
  - **состав комплексов**: `БАК (B03.014.004) ⊃ АЛТ, АСТ, …`, `исследование гормонов ЩЖ ⊃ ТТГ`.
    Его нужно составить: в перечне №123 состав комплексов не раскрыт. Он нужен для правил вывода
    (§2.5).
- **Диагнозы:** справочник МКБ-10 (`reference/icd10.json`, 15 038 записей НСИ) плюс синонимы из самих
  протоколов («тиреоидит Хашимото»). Поиск: точный → нечёткий (опечатки: «аутоимунный тереоидит») → эмбеддинги → LLM-выбор
  из короткого списка кандидатов.
- Сырые строки из `items` сопоставляются с каталогом тем же каскадом. Всё, что не сопоставилось
  уверенно, попадает в очередь проверки.

### 2.4 База знаний (`kb.sqlite`)

```
protocol(id, title, decree, date, population, category, path, sha256, status)
section(id, protocol_id, chapter, clause_from, clause_to, title, parent_section_id)
section_diagnosis(section_id, icd10, name)                 -- включая унаследованные
service(id, name, parent_id)                               -- каталог + иерархия
service_alias(service_id, alias)                           -- + FTS5 для нечёткого поиска
diagnosis_alias(icd10, alias)
prescription(id, section_id, service_id, level, condition,
             raw, quote, page, clause, check_status)       -- verified | uncertain (§2.2а)
```

SQLite + FTS5 (при желании sqlite-vec для эмбеддингов): один файл, без сервера, легко раздать
вместе с CLI или десктоп-версией.

### 2.5 Решатель (детерминированный)

Вход: `icd10[]`, `service_id`, `population`. Шаги:

1. Найти протоколы и разделы, где диагноз указан явно или через наследование.
2. Найти назначения для услуги: точное совпадение, затем через иерархию — если в протоколе
   указана группа («БАК»), а спросили часть («АЛТ»), ответ «входит в указанную группу».
3. Вердикт:

| Вердикт | Когда |
|---|---|
| ✅ Обязательная диагностика | level = mandatory |
| ✅ Дополнительная диагностика (по показаниям: …) | level = additional, условие из `condition` |
| ☑ Предусмотрено для наблюдения / перед лечением | level = monitoring / pre_treatment |
| ⚠ Не предусмотрено протоколом | совпадений нет; дополнительно приводится оговорка п. 4 об иных услугах по консультации специалиста и полный список того, что предусмотрено |
| ❓ Нужно уточнение | диагноз неоднозначен, есть протоколы и для взрослых, и для детей, или услуга не распознана |
| ⛔ Протокол не найден | на диагноз нет протокола в базе |

К каждому ответу прилагаются документ (название, постановление), глава и пункт, **дословная выдержка**,
**ссылка `URL#page=N`** (N — физическая страница PDF; ссылка открывает файл на нужной странице;
печатный номер страницы указывается дополнительно) и статус записи (`verified` / `uncertain`).

Как трактовать вердикты для страхового случая:
- обязательная диагностика — предусмотрено безусловно;
- дополнительная — предусмотрено «по показаниям». Показания из `condition` выводятся отдельно:
  страховщик сверяет их с медицинскими документами;
- «не предусмотрено» — сопровождается оговоркой п. 4 (иные услуги допускаются по результатам
  консультации врача-специалиста по протоколу сопутствующего заболевания). Поэтому система
  дополнительно ищет эту услугу в протоколах других диагнозов, указанных в случае.

### 2.6 Запрос и ответ

LLM-парсер (быстрая модель уровня Haiku) превращает свободный текст в
`{diagnosis_text, service_text, population?}`. Затем resolver, затем engine. Итоговый текст LLM может
пересказать, но вердикт и цитаты берутся строго из ответа engine. LLM не может «решить» иначе.

Пример для исходного вопроса:

> **Подсчет форменных элементов методом Нечипоренко (A09.28.060) — не предусмотрен** протоколом
> для диагноза «Хронический аутоиммунный тиреоидит» (E06.3).
> Источник: КП «Диагностика и лечение пациентов с заболеваниями щитовидной железы (взрослое
> население)», пост. МЗ №85 от 21.06.2021, гл. 6 «Тиреоидиты», пп. 73–74 —
> `https://minzdrav.gov.by/upload/dadvfiles/CProtokol/…_85.pdf#page=18` (стр. 18–19 PDF, печатн. 50).
> - Обязательная диагностика: УЗИ ЩЖ и регионарных л/у; ТТГ, АТ-ТПО.
> - Дополнительная: св. Т4, св. Т3, АТ-ТГ, АТ-рТТГ; ОАК; БАК (АЛТ, АСТ, СРБ); ТАБ ЩЖ; ЭКГ, ХМ-ЭКГ,
>   ЭхоКГ, СМАД; сцинтиграфия ЩЖ; КТ шеи и средостения; рентгенография ОГК; консультации хирурга и
>   кардиолога.
>
> Оговорка (п. 4): иные услуги могут назначаться по результатам консультации врача-специалиста
> в соответствии с протоколом сопутствующего заболевания.
> ❓ Пациент — ребёнок? Для детей действует другой протокол (пост. МЗ 2019 №90).

### 2.7 Обновления

Scraper отмечает изменённые документы (новый sha256) → parser и extractor обрабатывают только их →
`kb diff` показывает, какие назначения добавились, исчезли или изменились → эти записи получают
статус `draft` до проверки. Удалённые с сайта протоколы помечаются `status=removed` и в ответах
не используются, история сохраняется.

## 3. Интерфейс

Рекомендация — делать по шагам; ядро у всех вариантов общее:

1. **CLI** (`python kb.py ask "…"`, `kb.py build`, `kb.py review`) — сразу, для разработки и для
   проверки базы врачом. Выводит вердикт и цитаты.
2. **MCP-сервер** с инструментами `find_diagnosis`, `check_service`, `list_diagnostics`,
   `get_clause_text`. Это почти бесплатно даёт чат-интерфейс «как Claude Code» в Claude Desktop или
   Claude Code: LLM ведёт диалог и уточняет детали, а вердикт берётся из инструментов.
3. **Веб** (FastAPI + простая страница или чат) — для конечных пользователей без установки.
   Отдельное десктоп-приложение не нужно: веб или MCP закрывают этот сценарий.

Экран ручной проверки базы не нужен: врача нет. Вместо него — отчёт о расхождениях (§2.2а) для
разработчика. В интерфейсе страховщика у ответа есть кнопка «ответ неверен» с комментарием; такие
отметки попадают в эталонный набор (§4).

## 4. Качество

- **Эталонный набор**: 50–100 пар «вопрос → ожидаемый вердикт и пункт», включая ловушки:
  наследование (АИТ → гл. 6), группы (АЛТ ⊂ БАК), взрослые и дети, опечатки, «не предусмотрено»,
  диагноз без протокола. Прогоняется при каждом изменении базы или промптов.
- Метрики извлечения на размеченных вручную 10–15 протоколах: полнота и точность назначений.
- Для пользователя система — справочная. Дисклеймер: ответ основан на тексте протокола, а не на
  клиническом решении.

## 6. Выбор LLM: можно ли бесплатные или дешёвые модели

Нагрузок две, и они очень разные.

**Извлечение базы (офлайн).** Это разовая работа плюс обработка изменившихся протоколов. Корпус —
около 19 млн символов, оценочно 7–10 млн токенов на один полный прогон. Именно здесь решается
качество, а врача-проверяющего нет. Ошибки дешёвых моделей на длинном русском нормативном тексте
типичны и для нас критичны: пропуск пунктов в длинных списках, путаница «обязательная /
дополнительная», потеря наследования (гл. 12 → гл. 6), неверная привязка к перечню.

Ориентир по ценам Claude API на 2026-10 ($ за 1 млн токенов, вход/выход): Opus 5.5 — 4/20,
Sonnet 5.5 — 2/10, Haiku 5.5 — 0.10/0.50. Batch API даёт скидку 50%. Полный прогон всего корпуса
обойдётся примерно в десятки долларов на Opus и единицы долларов на Haiku. Цифры оценочные, точнее
покажет `count_tokens` на реальном корпусе. При таком масштабе экономить на модели для извлечения
нет смысла. Рекомендация:
- типовые протоколы разбирать правилами (бесплатно);
- LLM сильного класса (Opus) — для связи «раздел → диагнозы», наследования и условий;
- вторая, более дешёвая модель (Sonnet или Haiku) — как независимый второй прогон для
  перекрёстной проверки (§2.2а). Правила плюс дешёвая модель — уже сильная проверка.

**Ответ на запрос (онлайн).** LLM здесь только разбирает короткую фразу («диагноз — …, разрешён
ли …») и выбирает из 5–10 кандидатов, найденных нечётким поиском по словарям. Вердикт она не
выносит. С этим справляются дешёвые модели: Haiku — доли цента за запрос. Подойдут и бесплатные
локальные open-weight модели на 7–14B параметров, если нужна работа без интернета. Ошибка на этом
шаге видна сразу: в ответе указано, какой диагноз и какую услугу система распознала.

**Вывод:** бесплатная или дешёвая модель приемлема для онлайн-части. Для офлайн-извлечения её стоит
использовать только как второй, проверяющий прогон: основное качество базы обеспечивают правила
плюс сильная модель. Данные публичные, и в запросе нет персональных данных (только диагноз и
услуга), так что облачный API допустим. Если страховщик всё же будет вводить данные пациента, их
нужно вырезать до отправки в LLM.

## 7. Открытые вопросы

1. Учитывать ли уровень оказания помощи (районный / областной / республиканский) и условия

   важно.

   scraper хранит прежние версии в `_history/`, но без дат действия.
