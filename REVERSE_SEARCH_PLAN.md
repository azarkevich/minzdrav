# План: обратный поиск «услуги → диагнозы»

Статус: реализовано 2026-10-24, версия сайта 2.3 (детали и результаты — CLAUDE.md, раздел 5, «Reverse search»).

## Задача

Пользователь даёт одно или несколько исследований/анализов, система отвечает, при каких диагнозах
клинические протоколы МЗ их предусматривают — с кодами МКБ-10, уровнем (обязательно / по показаниям /
дифференциальная / наблюдение), цитатой и ссылкой в просмотрщик, плюс страховым вердиктом по диагнозу.

Примеры вопросов:
- «При каких диагнозах назначают сцинтиграфию щитовидной железы»
- «Для чего назначают метанефрины», «Метанефрины — при каком диагнозе»
- «ТТГ, свободный Т4, антитела к ТПО, УЗИ щитовидной железы» (перечень без диагноза)
- «HbA1c; глюкоза; C-пептид — какие диагнозы»

| метанефрины | 4 | 5 | E27, E26, D35, I10 |

Выводы: специфичные исследования дают точный ответ; общие (ОАК, ОАМ, БАК) встречаются почти везде —
нужно ранжирование по редкости и совпадению всего набора. Полный перебор — 2–3 с на запрос (на Render
дольше), нужен индекс.

## Шаги

### 1. Индекс «стем → разделы» (kb_pack.py / Engine)
- `kb_pack.py` (и `kb_build.py` при записи idx-формы) пишет `kb.stems.json`: `{stem: [section_idx, …]}` по
  стемам всех пунктов перечней (`level != "text"`) годных разделов (не `table`/`scan`, кроме `icd10_source == "table"`).
  `make_deploy.py` копирует его в `deploy/`.
- `Engine` грузит индекс, если есть; иначе строит при первом обратном запросе (локально, kb.json).
- Поиск кандидатов: для каждого обязательного стема услуги (`required_stems`) берём ключи индекса, которые
  `close`/`prefix_match` с ним (перебор ключей — десятки тысяч, быстро; так сохраняется терпимость к опечаткам),
  объединяем их разделы; пересечение по всем стемам услуги = кандидаты. Только у кандидатов читаем `items`
  (LazySection) и подтверждаем совпадение существующим `find()`.
- Цель: < 300 мс на запрос на Render, память + < 50 МБ (free-план 512 МБ, сейчас ~50 МБ).

### 2. Распознавание вопроса (`parse_reverse_question` в kb.py)
- Триггеры: «при каких (диагнозах|заболеваниях)», «при каком диагнозе», «для чего назначают», «какие диагнозы»,
  «показания к …», «в каких протоколах».
- Перечень без диагноза: текст режется по `,` `;` `+` переводам строк; режим «обратный», если ≥ 2 частей и каждая
  похожа на услугу (`resolve_service` находит услугу пост. №123, или есть стем из `GENERIC`/`METHOD`/`SERVICE_STEM_RE`,
  или аббревиатура из `data/abbreviations.json`), и ни одна часть не распознаётся как уверенный диагноз.
- Порядок в `Engine.ask`: обратный → перечень (list) → только диагноз → проверка. Не сломать существующие eval
  (golden/holdout/lists/insurance) — гонять после каждого изменения.
- `--llm`: при неуверенном разборе можно спросить LLM «это услуги без диагноза?» — не обязательно в первой версии.

### 3. `Engine.reverse_search(question, services: list[str], population=None)`
- По каждой услуге: найденные разделы + пункты (уровень, цитата через `cite`), `df` = число разделов.
- Раздел → «диагноз»: его `icd10` (до ~5 кодов, имя из МКБ) + `chapter_title`/`names`; разделы с
  `icd10_source == "protocol_scope"` ниже в выдаче (как tier 1), убирать, если есть разделы с собственными кодами.
- Оценка раздела: `Σ по совпавшим услугам weight(level) × idf(услуги)`, `idf = log(N / df)`,
  weight: mandatory 1.0, additional 0.8, listed 0.7, differential 0.5, monitoring 0.5.
  Сортировка: (доля совпавших услуг ↓, оценка ↓). Объединять разделы одного протокола с одинаковыми кодами.
- Группы по населению (взрослые / дети), как в других режимах; фильтр `population`.
- Ответ (`mode: "reverse"`): `services: [{text, catalogue, df, found}]`, `results: [{population, entries:
  [{diagnoses:[{code,name}], protocol, decree, url, chapter, chapter_title, matched:[{service, level, cite…}],
  missing:[service], coverage: "3 из 4", score}]}]`, `not_found: [service]`, `generic_warning` (все услуги
  общие — «ОАК есть в 711 разделах, добавьте специфичные исследования»), `method`. Топ-15 записей.
- Страховой вердикт по первому коду записи: `self.insurance.check(code, name)` → `verdict_level` + пункт.

### 4. Вывод
- `kb.render_reverse` (текст), `render()` отдаёт ему `mode == "reverse"`.
- `web/index.html`: `renderReverse(a)` — сверху распознанные услуги (найдена/не найдена, «встречается в N разделах»),
  ниже карточки диагнозов: коды + названия, «совпало 3 из 4», страховой тег (цвет как у вкладок), под ним совпавшие
  пункты с уровнем и ссылкой `view(url, quote)`, отдельно «не найдено в этом протоколе». Без вкладок страхования
  (вердикт — на каждой карточке). Пример в `EX`: «ТТГ, свободный Т4, антитела к ТПО — при каком диагнозе».
- Заголовок/подсказки в поле ввода: третий вид вопроса.
- `kb_web.summary` / Google Sheet: режим «обратный», услуги, топ-3 кода.
- `kb_mcp.py`: инструмент `find_diagnoses(services: string[], population?)`.

### 5. Проверки
- `eval/reverse.jsonl` (`mode: "reverse"`, `expect_any`: коды, из которых хотя бы один в топ-`top`), ~20 случаев, например:
  сцинтиграфия щитовидной железы → E05/E04 (top 3); метанефрины → E27/D35 (top 3); МРТ гипофиза → E22/E23/E24 (top 3);
  кариотип → Q96 (top 5); «ТТГ, св. Т4, АТ к ТПО, УЗИ щитовидной железы» → E06/E03/E05 (top 3);
  «HbA1c, глюкоза, C-пептид» → E10/E11 (top 3); спирометрия → J44/J45 (top 5); «ЭКГ, тропонин» → I20/I21 (top 5);
  «паратгормон, кальций, фосфор» → E20/E21 (top 3); плюс 3–4 вопроса-формулировки («для чего назначают …»).
  Часть случаев записать вслепую до настройки ранжирования (как holdout), остальные — после.
- `run_eval`: поддержка `mode: "reverse"`.
- `kb_probe.py`, новая проверка `reverse_self`: случайный раздел с собственными кодами, 2–3 его наименее частых
  пункта (по `df`) → обратный поиск должен вернуть этот раздел в топ-10. Плюс: существующие вопросы-проверки
  (`perturb`) не должны начать уходить в обратный режим.
- Регрессия: все существующие eval-наборы и `kb_probe` без ухудшений.

### 6. Документация и выпуск
- CLAUDE.md: раздел про обратный режим, `kb.stems.json`, версия 2.3. `make_deploy.py` → `deploy/kb.stems.json`.
- Коммит, push, на Render — Manual Deploy (автодеплой выключен), проверить в браузере.

## Открытые вопросы (решить по ходу, выбрать разумное по умолчанию)
- Разделы, привязанные к диагнозу только охватом протокола (`protocol_scope`): показывать ниже или скрывать.
- Услуги, упомянутые только в тексте протокола (`level == "text"`): в первой версии не учитывать.
- Очень длинные перечни (> 10 услуг): считать покрытие только по специфичным (`idf` выше порога).
- Таблицы старых протоколов (`kind: table`) участвуют только через строки таблиц, как в других режимах.

## Оценка
~1 рабочий день: индекс 1–2 ч, разбор вопроса 1 ч, поиск и ранжирование 2 ч, вывод (текст/веб/MCP) 2 ч, eval/probe 1–2 ч.
